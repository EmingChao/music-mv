# 附录 · 博主原版提示词卡（逐字转写）

> 这是抖音博主 Winhao学AI《MV 保姆级教程》里 10 张提示词卡的**逐字原文**，由视频抽帧转录。
> 保留原样是为了让你知道"人话版的需求"长什么样；**不要原样照抄去执行**，因为本 skill 已经把同样的意图
> 固化成更硬的约束（脚本、引擎、闸门）。下面这张表告诉你每张卡在今天对应哪一步、哪条命令。

| 原卡 | 视频里的目的 | 本 skill 里怎么落地 |
|---|---|---|
| 卡① 理解音乐 | Whisper 转 lyrics.srt + librosa 测 BPM + WebSearch 查乐评 | `./mv.sh analyze` + `./mv.sh lyric`；见 `references/lyrics-and-beats.md`（跳过 WebSearch：查乐评对画面没帮助，除非用户要） |
| 卡② 定画风 | 让 AI 按"反 AI 味"参数描述三种画风并出样图 | 三种画风已固化成 `templates/<style>/engine.js`；用户不确定就 `./mv.sh stills` 出样图 |
| 卡③ 画角色 | 角色存成 `character.js`，只留朝向/表情/动作三参数 | `CHARACTER-API.md` + `./mv.sh sheet` 设定图；这是"角色不漂移"的全部秘密 |
| 卡④上 剧本和分镜 | 写 `storyboard.md`：每句歌词一镜，写清动作与动机 | `references/storyboard.md` 的 9 列表（比原版多"卡哪一拍""怎么接下一个"） |
| 卡④中 转场 | 为**每两个相邻镜头**写明衔接方式（一镜到底/卡点切换/拼贴快切） | `assemble.js` 七种转场 + 分镜表第 9 列；见 `references/storyboard.md` §3 |
| 卡⑤上 先出草图 | 每镜一张关键帧拼 `storyboard.png`，人工确认再往下 | `./mv.sh stills` 出三帧 + `read_image`（G5 闸门） |
| 卡⑤下 做整片 | 一次合成完整片；背景/角色/道具同一画布，不许分层叠 | 本 skill 单路线：一帧一画布 → 逐帧渲 → 编片（`mv.sh render/encode/deliver`） |
| 清单 最常见的 5 个毛病 | 像幻灯片 / 转场硬 / 歌词错位 / 音画不同步 / 忽然变风格 | `references/pitfalls.md` + `references/review.md` 的六条过线标准 |
| 发布 发布前看一眼 | 分辨率、帧率、响度、黑帧 | `./mv.sh deliver` 自动 ffprobe 自检，末行 `DELIVER PASS` |
| 学风格（附加） | 给一支参考视频，抽帧 + 测节奏 + 六维风格清单 | `references/styles.md` §6 的 `STYLE-NOTES.md` 四件事 |

**两处口径差异（重要，别被原卡带跑）**：
1. 原卡让模型自己写 HTML/Canvas 并调 HyperFrames 合成；本 skill 去掉了这一层（弱模型 hold 不住），固定为"引擎 + 镜头脚本 + 装配页"。
2. 原卡蜡笔风用 p5.js + p5.brush（CDN 依赖）；本 skill 改成纯 Canvas2D 手写蜡笔，零外部依赖。

## 卡片编号体系（重要）

视频把流程拆成 **6 步**，但屏幕上只出现 **5 张卡编号**，其中两张各拆成上/下（或上/中）：

| 步骤 | 屏幕标注 | 卡片标签 |
|---|---|---|
| 第 1/6 步 | 第 1/6 步 · 理解音乐 | 卡① 理解音乐 |
| 第 2/6 步 | 第 2/6 步 · 定画风 | 卡② 定画风 |
| 第 3/6 步 | 第 3/6 步 · 画角色 | 卡③ 画角色 |
| 第 4/6 步 | 第 4/6 步 · 剧本和分镜 | 卡④上 剧本和分镜 → 卡④中 转场 |
| 第 5/6 步 | 第 5/6 步 · 草图与整片 | 卡⑤上 先出草图 → 卡⑤下 做整片 |
| 第 6/6 步 | 第 6/6 步 · 看成片、改 | 清单 最常见的 5 个毛病 + 发布 发布前看一眼 |

## 卡① 理解音乐 — 01:30 ~ 01:56（最佳帧 01:33）

代码块内为逐字转写。黄色高亮：`song.mp3`。

```
<role>你是 MV 的音乐分析师。</role>

<task>分析文件夹中的 song.mp3①：
1. 使用 Whisper 将歌词转写为带时间轴的字幕 lyrics.srt；文件夹中已有
   lyrics.srt 则直接使用
2. 使用 WebSearch 检索这首歌的歌词解读、乐评和听众评论，归纳出 3-5
   种主流理解，逐条附上来源链接
3. 综合上述理解，概括歌曲的主题与情绪走向
4. 使用 librosa 测出 BPM 与节拍点，标注前奏、主歌、副歌、
   停顿以及最后一个重音的时间点
结果整理为 song.md。 </task>

<check>将识别置信度低、可能有误的歌词单独列出，等我确认。 </check>
```

旁注 ①：**换成你的文件名**（红色圈 1，指向高亮的 `song.mp3`）。

观察细节：
- 这一段口播补充了卡面没写的东西：卡里只说"用 WebSearch 搜歌词解读"，口播明确说"他还会上网搜一搜，看看别人是怎么理解这首歌的，**整理几种常见的说法给你参考**"；并强调"**你也可以把自己的理解告诉他**"。
- 输出物是**两个文件**：`lyrics.srt`（带时间轴字幕）+ `song.md`（主题/情绪/BPM/节拍点/段落）。这两份文件后面每一步都在被引用（卡④ 读 song.md + lyrics.srt，卡⑤下 读 lyrics.srt 叠歌词）。
- 屏幕实际出现过的产物：`my-mv/` 文件夹里有 `song.mp3`、`lyrics.srt`（02:15 处可见，用来演示"导出字幕文件去给它理解"）。
- 刻意加了 `<check>` 让人工复核歌词——对应他讲的两个坑（见 02-ui-and-style-notes.md）。

## 卡② 定画风 — 02:46 ~ 02:57（最佳帧 02:52）

黄色高亮：`像素游戏风`、`纸艺拼贴绘本`、`蜡笔手绘绘本`（三处画风名）。

```
<role>你是 MV 美术指导。</role>

<task>基于 song.md 中的主题与情绪基调，用代码以下列 3
种画风分别绘制同一个开场画面，各输出一张 1920×1080 样例：
1. 像素游戏风①：使用 Canvas 2D 在 320×180 画布上逐格绘制，全片限定 16-
   32 色，渐变用抖动点阵，整数倍放大并关闭平滑；动画时角色逐帧换画、不做补间
2. 纸艺拼贴绘本：每个元素带剪纸白边或撕纸毛边和投影，层层叠放，
   底纹用旧报纸或牛皮纸；动画时画面每秒更新 8-12 次，每次随机抖动 1-2 像素
3. 蜡笔手绘绘本：使用 p5.js 和 p5.brush 的笔刷绘制，保留笔触和纸张纹理
每张附一句适配理由。完成后暂停，等我选择。 </task>

<avoid>使用图像生成模型；深色背景配霓虹光；紫色渐变；画面堆满文字。</avoid>
```

旁注 ①：**换成你想要的画风；只写风格名也行，画法让它自己定**（⍰ 该旁注只完整露出约 1 秒，词句按画面辨认，个别字可能有误）。

观察细节：
- 这是全片技术含量最高的一张卡：三种画风各自**规定了实现技术栈和"不像 AI 生成"的手法**：
  - 像素风 = Canvas 2D + 320×180 底图 + 16–32 色 + 抖动点阵 + 整数倍放大关平滑 + **逐帧换画不做补间**
  - 纸艺拼贴 = 剪纸白边/撕纸毛边/投影 + 旧报纸牛皮纸底纹 + **每秒 8–12 次更新 + 每次随机抖动 1–2 像素**（模拟定格动画的手作抖动）
  - 蜡笔绘本 = p5.js + **p5.brush** 笔刷，保留笔触与纸张纹理
- `<avoid>` 第一条就是"使用图像生成模型"——从根上锁死"这不是视频/图像生成器，是写代码画"。这与结尾"新 MV 背景用了 AI 生图"形成反差（见 02 笔记）。
- 口播原话："第一种就是像素游戏风，**歌词放进游戏的对话框里面**；第二种就是纸艺拼贴，有撕开的纸边和胶带，**歌词贴在纸片上**；第三种就是扁平绘本，还有蜡笔手绘，**我这两支水彩风 MV 就属于这一类**"。→ 三种画风的区别不只是笔触，**歌词的承载载体**也不同（对话框 / 纸片 / 手写）。
- 口播补充：三种画风"除了用 Opus 5.5 能做，其他模型也能做，不过效果可能就没那么好而已"；"不知道选哪种画风的，可以先让 Opus 5.5 出三张样图给你挑"。
- 屏幕上紧接着播放了三种画风的成片样例（02:26–02:41），见 02 笔记的画面描述。

## 卡③ 画角色 — 03:00 ~ 03:18（最佳帧 03:03）

黄色高亮：`一只橘色的小螃蟹`。

```
<role>你是角色设计师。</role>

<task>以选定画风设计这支 MV 的主角：一只橘色的小螃蟹①。
1. 将角色封装为独立模块 character.js，提供统一的绘制接口，
   参数包括朝向、表情、动作
2. 表情至少包括开心、害羞、难过 ； 动作至少包括走、跳、拥抱、手持道具
3. 输出一张角色设定图：正面、侧面、背面三视图加表情表，等我确认。
   后续所有镜头都通过 character.js 绘制角色，保证造型前后一致。
</task>

<avoid>每个镜头重新绘制角色；手持道具与手部分离；道具遮挡面部。</avoid>
```

旁注 ①：换成你的主角（原文只露出半句，⍰ 后段被遮挡；大意"有几个角色就写几个"）。

观察细节：
- **主角是"一只橘色的小螃蟹"**——就是画面里那个方头橘色小方块（作者叫它 Clawd）。豆包/其他总结里写的"作者 Clawd 31 表情 20 配饰"对应口播："那我这两支 Clawd 就是这么来的，那 31 种表情、20 种配饰全是代码画的。"
- 关键工程约束：角色必须是**独立模块 `character.js`**，对外只有统一绘制接口（朝向/表情/动作三参数），**所有镜头都从它取**，因此"角色就不会漂移"。这是全片最可迁移的一条工程经验。
- 卡③的输出是"三视图 + 表情表"的**设定图**（先看图确认，不是先写视频）。
- 注意 `<avoid>` 里"道具遮挡面部"和"手持道具与手部分离"——与第 6 步清单里的"道具不对"是同一个坑的两次出现。

## 卡④上 剧本和分镜 — 03:31 ~ 03:48（最佳帧 03:34）

```
<role>你是 MV 导演。</role>

<task>使用 HyperFrames 制作这支 MV，先按它的分镜流程输出
storyboard.md：
1. 以 lyrics.srt 的时间轴为准，每句歌词对应一个镜头，
   画面直接表现这句歌词的含义
2. 抽象的歌词拆解为观众看得懂的连续动作
3. 每个镜头标注起止时间、场景、角色动作与运镜方式，镜头切换对齐 song.md
   中的节拍点
4. 以下抽象歌词按我的理解表现：（写在这里）
整体叙事要有情感起伏，结尾留有余味。完成后暂停，等我确认。 </task>

<avoid>单句歌词安排多个动作；无信息量的过场；观众无法理解的情节。 </avoid>
```

旁注（卡片右侧，⍰ 只露出一部分）：① 抽象歌词在这里补一句你的理解，故事会稳很多。

观察细节：
- **这张卡没有 `<check>`**（全片只有卡①、卡④中、卡⑤下、学风格 四张带 `<check>`）。它靠 "完成后暂停，等我确认" + `<avoid>` 收口。
- **"用 HyperFrames 制作这支 MV"** —— 全片唯一一次点名工具链，且是"一句话点名"：作者口播"从这一部开始就可以使用到 HyperFrames 这个 skill，那跟它说用 HyperFrames 来做就可以了，**他会自己把要用的准备好**"；接着说"**他的流程第一步就是写分镜**，所以我把剧本和分镜放在一起写"。
- 卡面的第 4 条是**留白槽位**：`以下抽象歌词按我的理解表现：（写在这里）`——正好对应他踩的坑（抽象歌词不解释就会"好看但看不懂"）。
- 卡面写的是**四项具体字段**：起止时间 / 场景 / 角色动作 / 运镜方式；口播又补了一句"每一句歌词演什么、每个镜头几秒钟、怎么动，**一次性给他写清楚**"。
- `"整体叙事要有情感起伏，结尾留有余味"` 是一条很少见的"叙事节奏"约束，豆包总结里没有。
- 口播的痛点和解法："有些歌词是比较抽象的，AI 是很难理解里面的意境的，那你就可以把自己的理解告诉他"；"我前几版就是没有对抽象的歌词做说明，结果做出来的画面虽然很好看，但看完之后一头雾水，不知道他到底要讲什么。我前后**换了三个故事**才定下现在这个。"
- 补一句他给的后路："剧情你也可以按别的模型帮你出几版，不一定是 Opus 5.5，挑一个你最喜欢的就行。"

## 卡④中 转场 — 04:30 ~ 04:37（最佳帧 04:33）

卡面主题词"三种转场方案"黄色高亮，1–3 条整体被红框框住（示意"三种方案任选一"）。

```
<task>根据画风与歌曲节奏，从以下三种转场方案①中推荐一种并说明理由：
1. 一镜到底：整片由一台虚拟摄像机连续拍摄，通过推拉、上摇至天空、
   穿过门窗切换场景
2. 卡点切换：在节拍点切换镜头，用甩镜或前景物体扫过画面衔接
3. 拼贴快切：每 0.5-1 秒切换一张画面，新画面以卡片形式滑入、刷开
确定方案后，在 storyboard.md 中为每两个相邻镜头写明衔接方式。 </task>

<check>每次转场都有衔接：起点对齐节拍，承接角色动作或画面元素；
衔接帧前后角色的大小、位置、姿态一致，不发生瞬移；
镜头推拉时画面元素不突然消失或出现。 </check>

<avoid>无衔接的硬切；整屏叠化；镜头频繁来回推拉或晃动。 </avoid>
```

旁注 ①：**已经知道要哪种，就删掉另外两种，直接写"采用一镜到底"**（红字，贴在卡右侧）。

观察细节：
- 作者把这张单独拎出来叫"**干货，注意听**"，并给了量化证据："我第一支 MV **20 个镜头里面有 12 个地方**要么是硬切，要么就是整个画面叠化，看上去就很僵硬。"
- 解法就是这张卡的存在理由：**在写分镜的阶段就把"每两个镜头怎么衔接"一并写清**，而不是等到渲染完再救。
- 卡标题在视频里出现过两个版本：较早的帧里标"卡③ 转场"，最终定版为"**卡④中 转场**"（04:30 的过渡帧两者同框）。写 skill 时按最终版。

## 卡⑤上 先出草图 — 04:43 ~ 05:00（最佳帧 04:47）

```
<task>分镜已确认。暂不渲染成片：为每个镜头绘制一张关键帧草图，拼接为一张分镜总览图
storyboard.png 供我检查，确认后再制作完整视频。 </task>
```

观察细节（这张卡很短，但右侧配了真实产物截图，信息量在截图里）：
- 屏幕右侧展示真实的 `storyboard.png`（3 列 × 2 行可见，共 6 格示范；实际是每镜头一格），每格结构是：
  - 上半：该镜头的**关键帧草图**（已上色，不是线稿）
  - 下半左：**镜头号 + 主题**，如 `06 · 心跳`
  - 下半右：**帧号 + 时间码**，如 `frame-06 · 15.23-19.93`
  - 正文一句话写**这个镜头里发生什么 + 怎么动**，例：`先动：粉色的靠过去。特写：粉色的靠在原色身上闭着眼。原色身上一颗小爱心每拍跳一下，每跳一下树上落一片花瓣（花瓣在 HyperFrames 里，卡拍）。`
  - 底部一个**胶囊标签写转场方式**，例：`推近 + 焦点虚化接过去`

## 清单 · 最常见的 5 个毛病 — 05:10 ~ 05:25（最佳帧 05:20）

标题：`清单 最常见的 5 个毛病　截图保存 ✓`。讲这段时 1–4 条被红框逐条高亮。

```
1. 像幻灯片
   画面动态不足，像幻灯片。先用 ffmpeg 每 0.5 秒抽帧、
   计算相邻帧差，找出静止段落，再让角色持续有动作、
   镜头保持缓慢运动，每句歌词安排一个清晰的主要动作，以中近景呈现。

2. 运镜晃
   镜头运动过于频繁。每个镜头只保留一种缓慢运动：慢推、慢移或跟随角色。

3. 表现力不够
   情绪表现不足。情绪最强的段落改用近景，光线与色调随情绪变化。

4. 道具不对
   手持道具位置异常。道具须贴合手部，且不得遮挡面部。

5. 歌词没演出来
   「（这句歌词）」的画面未能表达歌词含义，请换一种更直观的表现方式。
```

观察细节：
- 这 5 条其实是**可直接复用的"审片 rubric + 修复咒语"**，每条都是"病名 → 诊断 → 改法"，第 5 条留了 `「（这句歌词）」` 占位符让人填具体那句。
- 第 1 条的诊断方法很硬核：**ffmpeg 每 0.5 秒抽帧计算相邻帧差，自动找出静止段落**——这是"像 PPT"的量化检测手段，值得直接写进 skill。
- 口播："这一步我改了 **9 版**，最常见的坑都被我踩了一遍。我整理成了一张清单，截图存下来，看到哪个毛病就把对应的提示词发给他改就可以了。"
